# GitHub Actions Release Guide

This project publishes desktop builds through GitHub Releases.

The release workflow is defined in `.github/workflows/release.yml`. It builds the macOS arm64 DMG/ZIP artifacts, publishes them to the GitHub Release, and verifies that `latest-mac.yml` points to real generated files.

## Why releases use tags

Auto-update must be based on versioned release artifacts, not raw commits.

Each update needs:

- a package version in `package.json`;
- a Git tag that matches that version, such as `v0.1.5`;
- a GitHub Release created from that tag;
- packaged artifacts, including the macOS ZIP used by updater metadata;
- `latest-mac.yml` generated by `electron-builder`.

This keeps unfinished commits from being sent to users.

## One-time repository setup

In GitHub, open:

`Settings` → `Actions` → `General` → `Workflow permissions`

Select:

`Read and write permissions`

Then save.

The workflow also declares:

```yaml
permissions:
  contents: write
```

That is required so the built-in `GITHUB_TOKEN` can create/update releases and upload artifacts.

## Publishing a release

1. Make sure the app is ready and committed.

2. Bump the version:

```bash
npm version patch --no-git-tag-version
```

For a minor or major version, use:

```bash
npm version minor --no-git-tag-version
npm version major --no-git-tag-version
```

3. Verify locally:

```bash
npm run build
```

4. Commit the version bump:

```bash
git add package.json package-lock.json
git commit -m "chore: release v0.1.5"
```

5. Create the tag:

```bash
git tag v0.1.5
```

The tag must match the package version exactly. `package.json` version `0.1.5` requires tag `v0.1.5`.

6. Push the commit and tag:

```bash
git push origin main
git push origin v0.1.5
```

GitHub Actions will start automatically.

## Manual workflow run

You can also run the workflow manually:

1. Open the repository on GitHub.
2. Go to `Actions`.
3. Select `Release`.
4. Click `Run workflow`.
5. Enter a tag such as `v0.1.5`.

The tag must already exist in the repository.

## Expected release assets

The GitHub Release should include:

- `Verboo-Code-<version>-arm64.dmg`
- a macOS `.zip` artifact
- `latest-mac.yml`

`latest-mac.yml` is the important file for updater clients. It must reference the generated ZIP artifact.

## Local validation

After local packaging, run:

```bash
npm run verify:update-release
```

This verifies:

- `release/latest-mac.yml` exists;
- the metadata version matches `package.json`;
- a DMG artifact exists;
- a ZIP artifact exists;
- artifact names include the version;
- names do not contain whitespace;
- metadata references files that actually exist.

## Unsigned macOS limitation

Current internal builds are ad-hoc/unsigned. They are useful for internal testing, but macOS Gatekeeper can still warn or block users on another Mac.

Developer ID signing and notarization should be added before broader public distribution. The GitHub Actions workflow is structured so signing credentials can be added later without changing the release model.

Future secrets likely needed:

- `APPLE_ID`
- `APPLE_APP_SPECIFIC_PASSWORD`
- `APPLE_TEAM_ID`
- `CSC_LINK`
- `CSC_KEY_PASSWORD`

When those exist, remove `CSC_IDENTITY_AUTO_DISCOVERY=false` from the release job and configure notarization in `electron-builder`.
